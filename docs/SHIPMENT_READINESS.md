## Repository inspection and dependency coverage

Repository inspection now loads the original root context files and supported dependency manifests at the root and one directory below. Root context files are prioritized; the 25-candidate cap includes context files such as `README.md`, and the response separately reports manifest and context candidate counts, scanned/omitted counts, and partial-coverage status. Per-file and aggregate read caps are 64 KB and 512 KB. Reads use the resolved default-branch commit, and the response includes both commit and tree revisions. Static direct dependency names are extracted from npm, Python, Go, Rust, Maven, Gradle, Ruby, and Composer manifests. Signed Dependabot version-update pull requests are recorded as bounded, deduplicated human-triage Signals using the PR title, number, branch, and verified GitHub URL; bodies are omitted and no code is executed. A scheduled dependency review now polls active GitHub repositories connected to the scheduled project for open Dependabot alerts, up to 10 repositories and 5 pages of 100 alerts per repository per run. Open alert events use the webhook source ID so polling deduplicates with `created` and `reopened` webhooks; a separate summary records the alert count or an explicit blocked/incomplete outcome. A permission failure, rate limit, provider error, repository cap, or page cap is never reported as zero alerts; GitHub 403 responses with Retry-After or X-RateLimit-Remaining: 0 are classified as rate limits, while other 403 responses are permission failures. The polling requires the connected GitHub credential to have Dependabot alerts read access. This remains alert discovery for human triage: it does not resolve versions, scan dependency manifests against advisories, create update branches, or apply patches. A closed alert does not automatically resolve an existing inbox signal. This branch adds migration 0065 and a tenant/project/repository-bound current-state projection for Dependabot alerts. The scheduler polls open, dismissed, fixed, and auto-dismissed states within the existing repository and page caps; incomplete scans and permission failures remain explicit outcomes. Provider `updated_at` markers order webhook and polling observations, stale deliveries cannot resurrect a newer closure, and a newly observed reopen re-arms an acknowledged signal once per provider revision. Stable source IDs keep webhook and poll observations deduplicated, including a poll-first reopen followed by its late webhook. PostgreSQL RLS checks bind each alert row to its organization, project, and actual connected repository. This change is pending review and CI on its exact PR head; the previous shipment assessment described the gap before this lifecycle projection.

## Release decision

The repository-to-agent-to-sandbox-to-draft-PR path has deterministic CI acceptance with a real sandbox container (PR #132); PR #133 fixes and tests production Compose worker sandbox access, and PR #134 adds privacy-safe execution spans for worker operations. Neither has been validated with a live model provider and configured GitHub installation. The Phase 10 Compose path and Kubernetes CI workflow are implemented, and CI passes a PostgreSQL backup/restore smoke test. Neither a controlled Kubernetes deployment nor a deployment-specific restore drill has been recorded. Kubernetes deployment also requires the operator configuration listed above. The new trace stack is a single-node, seven-day local baseline; its volume backup, alert routing, and deployment validation remain untested. The overall product is **not ready to ship as the AI engineering teammate described in `UPDATE.md`** until safe project dependency installation for verification, live provider-backed acceptance, remaining worker-recovery and operational gaps, and a controlled deployment with a deployment-specific restore drill are addressed. Dependency coverage includes bounded GitHub Dependabot alert polling for scheduled projects plus static manifest names; it does not resolve versions, conduct a full advisory scan, or apply updates. Private repository access still relies on one organization token without GitHub App installation-level permission mapping. The exact release scope should not be represented as a complete implementation of the product brief.
