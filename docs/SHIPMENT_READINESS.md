# Shipment readiness assessment

This status compares the repository with `UPDATE.md`, including its primary engineering workflow and Phase 10 self-hosting requirements. It is a code review snapshot, not a claim that every product requirement is complete.

## Phase 10: self-hosted deployment

| Requirement | Status | Evidence / remaining work |
|---|---|---|
| Docker Compose deployment | Implemented for a self-hosted baseline | `docker-compose.prod.yml` separates API, UI, database, Redis, migrations, scheduler worker, and sandbox supervisor. Requires an operator-managed TLS reverse proxy and host security controls. |
| Database migrations | Implemented in deployment path | The one-shot `migrate` service runs `alembic upgrade head`; API and worker wait for successful completion. |
| Persistent volumes | Implemented | PostgreSQL and Redis use named volumes. Off-host backup and recovery remain operator responsibilities. |
| Health checks | Partial | API liveness/deep-readiness, frontend, PostgreSQL, and Redis health checks. Scheduler heartbeats persist to PostgreSQL and `/api/v1/health/workers` reports healthy, stale, and stopped instances. A heartbeat is an operations signal, not proof of queue recovery. |
| Backup and restore | Scripts and procedure implemented | Backup omits credentials from logs, supports asyncpg URLs, and uploads to S3 only when configured. Restore requires exact target confirmation and does not drop the database. No automated schedule, retention service, or restore drill is supplied. |
| Secure configuration | Baseline implemented | Production example requires separate auth, encryption, webhook, and database secrets; API fails to start when core auth secrets are absent. Secret storage/rotation remains deployment-specific. |
| Observability | Partial | Structured logs and Prometheus metrics exist. Compose does not include a metrics collector, durable trace backend, or alert routing. Worker heartbeat is available through the health API. |
| Worker management | Partial | Scheduler is a separate, restartable singleton service with persisted process heartbeats. Durable scheduled workflow state and leases exist; queue dashboard, concurrency controls, and dead-letter operations remain follow-up work. |
| Resource controls | Implemented at container level | Compose configures CPU and memory limits. Production verification dispatches from the API to a private sandbox supervisor, which creates networkless bounded job containers. Repository workspaces support selected GitHub files or a shallow full checkout pinned to the REST-resolved commit, capped at 20,000 tree entries / 48 MiB of source and 128 MiB of workspace data. Symlinks, submodules, unsupported modes, and non-text changes in delivery remain unsupported. |
| Teammate workspace tools | Partial | Active handoffs can request list/read with `READ_ONLY` and write/delete with `MODIFY_FILES`. Fixed verification profiles create durable approval requests bound to the exact workspace digest and command. An owner/admin reviews the request; a worker then claims approved work, recovers interrupted attempts with fenced leases, and dead-letters after three interrupted attempts. Arbitrary teammate shell execution remains unavailable. |
| Sandbox control boundary | Implemented for the Compose baseline | Only the trusted supervisor receives `/var/run/docker.sock`; untrusted job containers, API, worker, and frontend do not. The supervisor has Docker host control authority. Current Compose is co-located and needs a shared volume; a separate physical runtime host is not supported yet. |
| Production documentation | Implemented for Compose baseline | `DEPLOYMENT.md` covers setup, migrations, proxy placement, backups, restore, and limits. It is not a substitute for a deployment-specific incident and recovery runbook. |

## Product shipment blockers

The central `UPDATE.md` workflow is not complete. The sandbox supports seeding a task workspace with caller-selected public GitHub files or private GitHub files through the active organization credential linked to that repository, pinned to one commit SHA and scoped through the delegated task's project handoff, with source provenance persisted. Full repository mode performs a shallow Git checkout after tree preflight, uses filtered temporary authentication, disables hooks and prompts, rejects unsafe paths, symlinks, submodules, and unsupported modes, and checks out only when the fetched commit matches the REST-pinned SHA. Repository files are streamed from Git objects without applying Git attribute filters, preserving raw GitHub blob bytes. Delivery compares changed files against GitHub tree blob hashes instead of trusting the mutable local `.git` directory. During an active delegated handoff, teammates can list/read files under `READ_ONLY` and write/delete files under `MODIFY_FILES`; writes and deletions pause while a verification approval is pending, approved, or running. Under `EXECUTE_COMMANDS`, teammates can request fixed test/build/lint/typecheck/security profiles, which require an owner/admin decision before the sandbox runs. The approval records the exact argv and workspace digest, and execution rejects a changed workspace. Tool invocation metadata and verification outputs are persisted.

For repository-backed workspaces, an owner/admin can use the task review page to inspect the diff and submit the displayed digest to create a Solvyn branch from the exact pinned source commit, commit up to 50 UTF-8 text file operations / 500 KB, and open a draft PR. A deletion is allowed only for a selected regular, non-executable text file present in the pinned source; unsupported missing paths remain blockers. The preview binds the current GitHub base branch as well as the workspace; a changed preview invalidates the delivery request. The endpoint will not merge. Changed executable files and edits to unselected existing paths are rejected. Each digest-bound delivery attempt is persisted with branch, commit, PR, and outcome status; repeat requests replay the saved creation result without claiming the PR's current state, or stop for recovery when a prior outcome is unresolved. If a GitHub write times out after it may have succeeded, the endpoint records an unknown outcome and recovery guidance rather than claiming no remote change was made. The task review page includes a bounded activity feed for task lifecycle events, tool records, verification runs, related handoffs and approvals, and delivery attempts across the task's descendants. Lifecycle events are captured atomically for task creation and status changes; existing tasks receive a point-in-time status baseline, not fabricated historical transitions. Tree traversal is capped at 500 tasks / 32 levels, and the feed is capped per source and overall. Live GitHub status refresh currently applies to the requested task's PRs; descendant PRs show saved delivery state without a live refresh.

Shipment blockers remain: complete PostgreSQL row-level security coverage; complete task-tree execution history beyond lifecycle transitions; proactive maintenance that runs checks rather than only creating triage events; durable worker recovery, queue/dead-letter operations, and concurrency controls; and deployment validation, backup scheduling, retention, and a restore drill. The current PostgreSQL RLS tranche protects task acceptance criteria, task delivery records, task workspace metadata, teammate tool invocation records, task dependency edges, verification run evidence, structured task handoffs, persistent teammate memory, workflow sessions, workflow execution graphs linked to those sessions, task lifecycle events, legacy agent instances, artifacts, session messages, and project memberships with transaction-local tenant context and fail-closed policies. Dependency policies verify both task endpoints; verification policies verify the task and workspace match the active tenant; handoff policies verify the parent/child relationship, project, assigned teammate, and their tenant/organization boundaries; teammate-memory policies verify tenant and organization consistency and require a current teammate/project assignment for memory access and writes. Removing an assignment hides that project’s teammate memory under RLS while retaining it for a future reassignment. Task create/status events are inserted by a database trigger in the task transaction; runtime inserts and event mutation are blocked. Migration baselines record current status without inventing prior transitions. Workflow executor, session, and compatibility routes bind the authorized tenant before protected session and execution queries; scheduling binds the owning tenant before writing execution graphs, and scheduler due-work discovery enumerates active tenants and binds each tenant before selecting its sessions. Admin session aggregates run under each explicitly selected tenant, and session cost analytics first verifies that the session belongs to the caller’s tenant. Compose and Kubernetes examples separate a non-superuser migration owner from the API runtime role, which receives data privileges but cannot change policies. The ORM inventory now has forced RLS on 34 of 38 tables; the four exceptions (tenants, users, refresh_tokens, and workflow_worker_heartbeats) are global identity, authentication, or operations records. PostgreSQL integration coverage now exercises signed webhook fan-out and scheduled-maintenance event writes under the non-bypass runtime role, asserting tenant-isolated visibility and schedule advancement. Verification due-run discovery/claim and broader worker recovery still need direct adversarial coverage. Private repository access currently depends on one organization token and bounded checkout limits; it does not offer GitHub App installation-level permission mapping. Verification approval is implemented as an inbox checkpoint. The current worker tranche automatically claims approved runs, resumes interrupted attempts with fenced leases, and dead-letters runs after three interrupted attempts; the wider queue-operations and recovery surface still needs validation. These gaps mean Solvyn cannot yet provide the complete engineering-teammate workflow in `UPDATE.md` as a production-ready product.

The latest RLS tranches also protect the central `tasks` and legacy `memory` tables. Task visibility is fail-closed, session and execution links must resolve within the same tenant/session, and a composite foreign key enforces same-tenant parent links. Memory is scoped by tenant and any linked session must belong to that tenant. Both migrations validate existing relationships before enabling policies. Verification task lookup binds the resolved tenant before its first query, including the shared-secret default-tenant path. Agent-memory, checkpoint, and audit operations now bind and filter by tenant, including vector search and local audit CLI access. These changes narrow the RLS blocker but do not close it; the remaining worker-path validation is described above.

## Release decision

The Phase 10 Compose path is implemented, but still needs deployment validation in a controlled environment. The overall product is **not ready to ship as the AI engineering teammate described in `UPDATE.md`** until the repository-to-agent-to-sandbox workflow is completed, tenant isolation and operational gaps are addressed, and a deployment validation is recorded. The exact release scope should not be represented as a complete implementation of the product brief.
